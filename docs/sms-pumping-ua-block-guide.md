# SMS 펌핑 공격 대응 — 인증 발송 전 User-Agent 차단 (타 프로젝트 공유용)

> 작성일: 2026-07-30
> 출처: plan-landing (SMS 인증 기반 상담 신청 랜딩)
> 대상: **SMS 인증번호 발송 API를 가진 모든 프로젝트**
> 목적: 동일 공격자에게 당하기 전에 같은 방어막을 미리 깔아두기 위한 맥락 + 차단 목록 전달

---

## 1. 맥락

### 무슨 일이 있었나

SMS 인증번호 발송 API(`POST /api/sms/send-code`)가 **SMS 펌핑(SMS pumping) 공격**을 받았다. 공격자가 봇으로 발송 API를 반복 호출해 문자를 대량 발송시키는 방식이며, 피해는 **발송 요금 전액**이다.

측정된 규모는 다음과 같다.

- 60시간 동안 발송 **722건 중 701건(97%)이 단일 공격자**의 봇 트래픽. 정상 사용자 발송은 21건뿐.
- 요청 간격 중앙값 **90초**로 기계적 정속, **심야 포함 24시간 무휴** 가동.
- 수신번호 **701건 전부 유니크**(재사용 0회) — 구매한 번호 DB를 순차 소진하는 방식.
- 국내 유선 대역 **레지덴셜 프록시 풀** 사용. IP 262개지만 /24 서브넷 기준 29개에 불과하고, 같은 IP 재사용 간격 중앙값 218분으로 per-IP 레이트리밋을 의도적으로 회피.
- 발송 후 **verify(인증확인) 호출은 단 한 번도 없음** — 인증이 목적이 아니라 발송 자체가 목적임을 보여주는 지문.

### 왜 하필 UA 차단인가

기존 방어막이 이 공격에 전부 무력했기 때문이다.

| 방어막 | 왜 뚫렸나 |
|---|---|
| 전화번호당 레이트리밋 (시간당 N회, 쿨다운) | 번호를 **전량 1회용**으로 쓰므로 애초에 걸리지 않음 |
| IP당 레이트리밋 | 프록시 풀로 IP를 분산, 재사용 간격까지 벌려서 회피 |
| Turnstile / CAPTCHA | 60시간 중 차단 **2건뿐**. 대부분 유효 토큰으로 통과 (토큰 파밍 또는 헤드리스 브라우저 우회 추정) |
| 발송량 경보 | 사후 인지만 가능, 차단 기능 없음 |

반면 UA는 즉시 효과가 있었다. 공격 트래픽의 UA가 정상 사용자와 **완전히 겹치지 않았다**. 국내 정상 사용자는 삼성 브라우저·안드로이드 인앱 웹뷰(네이버/카카오 유입)·Edge·웨일을 쓰는데, 공격자는 Firefox를 썼고 정상 사용자 중 Firefox 사용자는 **0명**이었다.

즉 UA 차단은 **"제대로 된 방어"가 아니라 "지금 당장 요금 출혈을 막는 지혈대"**다. 도입 근거는 정교함이 아니라 즉시성이다.

### 공격자는 차단을 인지하고 UA를 바꾼다

이게 이 문서에서 가장 중요한 부분이다. 로그에 공격자가 차단에 실시간 대응하는 과정이 남아 있다.

| 시각 (UTC) | 행동 |
|---|---|
| 07-28 09:47~13:58 | Firefox 모바일 UA로 55건 공격 |
| 07-28 15:33~22:05 | 차단된 `Chrome/150` UA로 재시도 → 403 누적 9건 → **차단 인지** |
| 07-29 05:54~ | Firefox 데스크톱 UA로 전환, **속도 2배** 증가 |

- Firefox 버전도 `150`/`152`/`153`을 섞어 사용 → **버전 로테이션이 준비된 봇**.
- 모바일 시기의 IP 44개 중 43개가 데스크톱 시기에도 재사용 → 동일 운영자 확정.

따라서 UA 목록은 **한 번 넣고 끝나는 설정이 아니라 계속 갱신해야 하는 운영 대상**이다. 차단 로그에 UA 원문을 남기고 주기적으로 확인해야 한다.

### 검사 위치

전화번호 형식 검증 **직후**, Turnstile/CAPTCHA 검증 **직전**에 둔다. Turnstile보다 앞에 둬야 차단된 요청이 외부 검증 API 호출 비용을 발생시키지 않는다.

```ts
// 1) body 파싱 / 필수값 검증
// 2) ★ UA 차단  ← 여기
// 3) Turnstile 검증
// 4) 중복 신청 확인
// 5) 레이트리밋
// 6) SMS 발송
```

구현은 문자열 비교 두 줄이면 된다.

```ts
// ── 임시 응급조치: SMS 펌핑 공격 UA 지문 차단 ──
// 완전일치 전용. Chrome 계열은 반드시 여기에만 넣는다(아래 오탐 주의 참조).
const BLOCKED_UA_EXACT = new Set<string>([
  /* 2절 표 참조 */
])

// 계열 전체를 부분일치로 차단. 완전일치로는 버전만 바꿔 즉시 우회되는 경우에만 사용.
const BLOCKED_UA_INCLUDES = ['Firefox/']

const userAgent = req.headers.get('user-agent') ?? 'unknown'

if (
  BLOCKED_UA_EXACT.has(userAgent) ||
  BLOCKED_UA_INCLUDES.some((fingerprint) => userAgent.includes(fingerprint))
) {
  // UA 원문을 반드시 남긴다 — 다음 로테이션을 추적하는 유일한 단서
  console.warn(`[sms/send-code] ua-blocked | ip=${ip} | phone=${phone} | ua=${userAgent}`)
  return NextResponse.json(
    { error: '보안 정책에 따라 차단되었습니다. 다른 브라우저로 시도해주세요' },
    { status: 403 },
  )
}
```

### 한계 — 이것만으로 끝내면 안 된다

- 공격자가 삼성 브라우저나 인앱 웹뷰 UA로 위장하면 **UA 시그널은 완전히 사라진다.** 지금 UA로 구분되는 건 공격자가 트래픽에 섞이려는 노력을 안 했기 때문일 뿐이다.
- UA는 클라이언트가 자유롭게 보내는 값이므로 근본적으로 신뢰할 수 없다.

병행해야 할 구조적 대응을 효과 순으로 적는다. UA와 달리 **공격자가 UA를 바꿔도 유효**하다.

1. **/24 서브넷 레이트리밋** — 서브넷당 일일 발송 상한(예: 5건). 공격 서브넷은 즉시 걸리고, 정상 사용자는 통신사 모바일 대역이라 겹치지 않는다.
2. **verify 미수행 블랙리스트** — 발송 후 N분 내 verify 시도가 없는 IP/서브넷에 누적 점수를 매겨 차단. 공격자의 행동 자체가 시그널이라 UA 변경으로 우회 불가.
3. **CAPTCHA 강화** — managed/interactive 모드 전환, 토큰 1회용(재사용 불가) 검증 여부 점검.
4. **야간 강화 모드** — 심야(KST 01~07시) 트래픽이 사실상 100% 공격이면 해당 시간대만 임계치를 대폭 낮춘다.

## 2. 차단 UA 목록

규칙은 **완전일치**와 **부분일치** 두 종류다. 기본은 완전일치이며, 부분일치는 완전일치로 열거하면 버전만 바꿔 즉시 우회되는 경우에만 쓴다.

### 2-1. 완전일치 목록

UA 문자열이 **정확히 같을 때만** 차단한다.

| # | User-Agent 문자열 | 사유 / 주의 |
|---|---|---|
| 1 | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/150.0.0.0 Safari/537.36` | 최초 확인된 펌핑 공격 UA 지문. 위험도 낮음 |
| 2 | `Mozilla/5.0 (Linux; Android 10; K) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/150.0.0.0 Mobile Safari/537.36` | 펌핑 우회 대응으로 추가(2026-07-23). ⚠️ **stock 안드로이드 크롬의 매우 흔한 UA와 완전 동일** → 실제 모바일 고객도 차단될 수 있다. 모바일 유입 비중이 높은 프로젝트는 그대로 복사하지 말고, verify 성공률을 모니터링하며 판단할 것 |
| 3 | `Mozilla/5.0 (Linux; Android 10; K) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/138.0.0.0 Whale/3.9.14.9 Mobile Safari/537.36` | 웨일 모바일 UA를 위장한 펌핑 공격(2026-07-24). 실제 웨일 사용자와 충돌 가능하나 버전이 특정되어 위험도는 중간 |

### 2-2. 부분일치 목록

UA에 해당 문자열이 **포함되면** 차단한다.

| # | 포함 문자열 | 사유 / 주의 |
|---|---|---|
| 1 | `Firefox/` | Firefox 계열 전체 차단(2026-07-30 추가). 공격자가 Chrome 차단 인지 후 Firefox로 전환하고 `150`/`152`/`153`을 섞어 로테이션 중이라, 개별 버전을 완전일치로 넣으면 버전 하나 올려서 바로 우회된다. ⚠️ **실제 Firefox 사용자를 전부 차단**하므로 도입 전 아래 검증 필수 |

참고로 로그에서 관찰된 Firefox UA 원문은 아래 4종이며 **전부 공격 트래픽**이었다. 이 4개를 목록에 넣으라는 뜻이 아니라, `Firefox/` 규칙이 잡아낸 실제 사례다.

- `Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:153.0) Gecko/20100101 Firefox/153.0` (주력)
- `Mozilla/5.0 (Android 12; Mobile; rv:153.0) Gecko/153.0 Firefox/153.0` (모바일)
- `Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:152.0) Gecko/20100101 Firefox/152.0`
- `Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:150.0) Gecko/20100101 Firefox/150.0`

### 2-3. 오탐 주의 — 부분일치 추가 규칙

**Chrome 계열 문자열은 절대 부분일치로 넣지 말 것.** Edge·웨일·삼성 브라우저·인앱 웹뷰 등 정상 브라우저 UA가 `Chrome/...`을 그대로 포함하기 때문에, `Chrome/`이나 `Chrome/150`을 부분일치로 넣으면 정상 사용자가 대량 차단된다. 이 프로젝트에서 Chrome 지문 3개를 굳이 완전일치로 유지하는 이유가 이것이다.

`Firefox/`가 부분일치로 안전했던 것은 국내 정상 사용자 UA에 그 문자열이 등장하지 않았기 때문이며, **프로젝트마다 다를 수 있다.** 새 지문을 부분일치로 추가하기 전에 자기 로그로 충돌 여부를 먼저 확인한다.

```bash
# 후보 문자열이 정상 사용자 UA와 겹치는지 확인
# (아래는 SamsungBrowser/Edg/Whale/NAVER 인앱 UA와 'Firefox' 충돌을 검사한 예)
for b in SamsungBrowser "Edg/" Whale NAVER; do
  echo "$b: $(grep "$b" access-log.csv | grep -c 'Firefox') 건 충돌"
done
```

plan-landing 검증 결과는 전 계열 **충돌 0건**이었다(SamsungBrowser 32건, Whale 27건, NAVER 인앱 24건, Edg/ 4건 중 `Firefox` 동시 포함 0). 한 건이라도 충돌이 나오면 부분일치로 쓰면 안 된다.

> 로그 grep 시 주의: 정상 UA에 포함된 `KHTML, like Gecko`의 **쉼표** 때문에 CSV를 쉼표로 자르는 패턴은 UA를 중간에서 끊어버린다. UA 필드를 통째로 다루거나 문자열 포함 검사만 할 것.

### 2-4. 차단 동작

- 조건 충족 시 **403**과 함께 `보안 정책에 따라 차단되었습니다. 다른 브라우저로 시도해주세요` 반환.
- 서버 로그에 `ua-blocked | ip=... | phone=... | ua=...` 기록. **UA 원문을 반드시 포함**해야 다음 로테이션을 추적할 수 있다.
- 차단 사실을 응답 본문에서 구체적으로 알리지 않는다(어떤 UA가 막혔는지 노출하면 우회를 돕는다).
