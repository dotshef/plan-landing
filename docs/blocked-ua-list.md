# User-Agent 화이트리스트 정책

> 코드 위치: [src/app/api/sms/send-code/route.ts](../src/app/api/sms/send-code/route.ts) (`ALLOWED_UA_INCLUDES`)
> 상태: SMS 인증번호 발송 API(`/api/sms/send-code`)에 적용된 **UA 화이트리스트**. 근거: [SMS 펌핑 분석·전략](sms-pumping-2026-08-31-incident-and-strategy.md)
> 전환 이력: 2026-07~08 UA **블랙리스트**는 공격자가 4차례 UA를 갈아타며 우회(Chrome150→stock크롬→웨일→Firefox→Edge152 정품)해 폐기. 2026-08-31 A-2 광고세션 게이트를 시도했으나 공격자가 가짜 광고 랜딩으로 세션을 발급받아 우회 → 롤백. 현재는 화이트리스트 방식.

## 동작

요청 헤더 `user-agent`가 아래 허용 토큰 중 **하나라도 포함**하면 발송을 허용하고, 그렇지 않으면 `403`(사유 비노출: `요청을 처리할 수 없습니다. 잠시 후 다시 시도해주세요.`)으로 차단한다. Turnstile 검증 **이전**에 검사하므로 차단된 UA는 Turnstile 호출 비용도 발생시키지 않는다. 차단 시 서버 로그에 `[sms/send-code] ua-not-allowed | ip=... | phone=... | referer=... | ua=...`를 남긴다.

**부분일치 토큰 방식인 이유:** 전 UA 완전일치 화이트리스트는 기기 모델(SM-*)·앱 버전 조합이 수백 종이라 운영 불가. 국내 인앱 브라우저의 고유 마커 토큰으로 판별한다.

## 허용 토큰 (`ALLOWED_UA_INCLUDES`)

| 토큰 | 대상 | 8/31 로그 정상/공격 |
|---|---|---|

| `KAKAOTALK/` | 카카오톡 인앱 | 2 / 0 |
| `DaumApps/` | 다음 앱 | 2 / 0 |

## 설계 근거 (2026-08-31 로그 검증)

- 현재 공격은 **데스크톱 Windows Edge 152 정품 UA 단일**. 실고객은 대부분 **모바일 인앱 브라우저**. 둘을 가르는 실제 축은 브랜드가 아니라 모바일 인앱 여부다.
- 이 화이트리스트 기준: **공격 1,474건 100% 차단**, 정상 후보 36건 중 27건 통과(**~75%**). 차단되는 25%는 일반 모바일 크롬 4건 + 데스크톱 5건 — 감수하기로 한 트레이드오프.
- 구글 광고 유입 10건 중 6건은 네이버 앱 등 인앱으로 들어와 통과(표본 작음, 오차 있음).

## 한계와 운영

- **UA는 위조 가능 → 스토프갭이다.** 공격자가 허용 토큰(예: `KAKAOTALK/`, `SamsungBrowser/`) 문자열을 UA에 복사해 넣으면 즉시 무력화된다. 7월에 stock 안드로이드 크롬·웨일 모바일로 위장한 전례가 있다. 근본 대응은 총량 상한(서킷브레이커) 등 UA와 무관한 축이다.
- **채널 확대 시 토큰 추가:** 인스타/페북 광고를 돌리면 `FBAN/`·`FBAV/`·`Instagram`, 라인은 `Line/`, iOS 크롬은 `CriOS/` 등을 추가한다. 추가 전 정상 UA 로그로 충돌(오탐) 여부를 확인한다.
- **모니터링:** verify-code 성공 건수가 급감하면 실고객 오차단 신호 → 토큰 완화 검토(예: 일반 모바일 `Mobile Safari/537.36` 추가 = 모바일-only로 완화). `ua-not-allowed` 로그에서 통신사 IP·정상 referer 비율을 함께 본다.
