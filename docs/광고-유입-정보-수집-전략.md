# 광고 유입 정보(ad attribution) 수집 전략

리드 폼 제출 시 "이 고객이 어느 광고를 타고 들어왔는지"를 DB에 함께 적재하는 방식.
다른 랜딩 프로젝트에 그대로 이식할 수 있도록 원칙 → 구현 → 이식 체크리스트 순으로 정리한다.

---

## 1. 핵심 원칙

| 원칙 | 이유 |
|---|---|
| **최초 진입 URL 1회만 캡처** | 사용자가 사이트 내에서 이동하면 쿼리스트링이 사라진다. 폼 제출 시점에는 이미 파라미터가 없다. |
| **sessionStorage에 보관** | 같은 탭 = 한 번의 방문. 탭을 닫으면 소멸하므로 오래된 유입 정보가 다음 방문에 섞이지 않는다. |
| **매체(source)를 먼저 판정, 그다음 매체별 필드** | 구글/네이버는 파라미터 체계가 완전히 다르다. 매체가 정해지지 않으면 어떤 필드도 신뢰할 수 없다. |
| **클라이언트 값은 서버에서 다시 정규화** | 폼 payload는 위조 가능. 서버가 길이·화이트리스트·매체 정합성을 재검증한다. |
| **유입 정보 없음 = 저장 실패가 아님** | 광고 외 유입(직접/자연검색)은 `unknown`으로 정상 저장. 첨부 정보 때문에 리드를 잃지 않는다. |

---

## 2. 데이터 모델

```sql
alter table report_request
  add column traffic_source     text not null default 'unknown',  -- google | naver | unknown
  add column ad_keyword         text,   -- 네이버: 검색 키워드 (n_query)
  add column ad_campaign_id     text,   -- 구글: 자동 태깅 캠페인 숫자 ID (gad_campaignid)
  add column ad_campaign_label  text,   -- 구글: 최종 URL에 직접 넣은 라벨 (c=cam4)
  add column landing_url        text;   -- 공통: 최초 진입 전체 URL (원본 보존용)

alter table report_request
  add constraint report_request_traffic_source_check
  check (traffic_source in ('google', 'naver', 'unknown'));
```

**컬럼 설계 의도**

- `traffic_source`는 `not null default 'unknown'` — 이 컬럼만은 항상 값이 있어야 집계 시 누락이 안 생긴다.
- 나머지는 전부 nullable. **매체마다 채워지는 컬럼이 다르기 때문에 sparse한 게 정상이다.**
- `ad_campaign_id`(자동 태깅 숫자 ID)와 `ad_campaign_label`(사람이 지정한 이름)을 **분리**한 게 포인트.
  숫자 ID는 광고 계정과 대조해야 의미를 알 수 있고, 라벨은 그 자체로 읽힌다. 둘 다 남긴다.
- `landing_url`은 스키마가 못 따라가는 신규 파라미터에 대한 보험. 나중에 새 파라미터가 필요해지면
  과거 데이터도 여기서 파싱해 복구할 수 있다.

실제 마이그레이션 이력: `0004`(source + keyword) → `0005`(campaign_id + landing_url) → `0007`(campaign_label).
**한 번에 완성하지 않고 필요할 때 컬럼을 덧붙이는 방식**이 이 도메인에 맞다 — 광고 파라미터는 계속 늘어난다.

---

## 3. 매체 판정 규칙

파라미터의 **존재 여부**만으로 판정한다. 값은 보지 않는다.

```ts
const isGoogle = ['gclid', 'gbraid', 'wbraid', 'gad_campaignid'].some(k => params.has(k))
const isNaver  = ['n_media', 'n_ad_group', 'n_ad', 'napm'].some(k => params.has(k))

if (isGoogle === isNaver) return UNKNOWN   // 둘 다 없음 또는 둘 다 있음 → 판정 불가
```

`isGoogle === isNaver` 한 줄이 **둘 다 없음**과 **둘 다 있음(파라미터 오염/수동 조작)**을 동시에 걸러낸다.
애매하면 `unknown`으로 떨어뜨린다 — 잘못된 매체로 집계하느니 미상이 낫다.

**매체별 추출 필드**

| 매체 | 판정 파라미터 | 추출 |
|---|---|---|
| 구글 | `gclid`, `gbraid`, `wbraid`, `gad_campaignid` | `gad_campaignid` → `ad_campaign_id` / `c` → `ad_campaign_label` |
| 네이버 | `n_media`, `n_ad_group`, `n_ad`, `napm` | `n_query` → `ad_keyword` |

> 구글은 키워드를 URL로 넘겨주지 않으므로 `ad_keyword`가 항상 null이다. 키워드가 필요하면
> `{keyword}` ValueTrack 파라미터를 최종 URL에 직접 넣어야 한다.
> 네이버는 캠페인 ID 대신 검색어를 그대로 준다. **비대칭이 정상이다.**

## 4. 처리 흐름

```
[최초 진입]  ?gclid=...&gad_campaignid=123&c=cam4
     │
     ├─ 마운트 시 1회: sessionStorage에 값이 없을 때만 캡처 → 저장
     │   (unknown이면 저장하지 않음 = 나중에 광고 링크로 재진입하면 그때 캡처)
     │
[사이트 내 이동 → 쿼리스트링 소멸]
     │
[폼 제출]
     ├─ sessionStorage에서 읽어 폼 payload에 첨부
     │   읽을 때도 매체별로 필드를 재구성 (손상된 JSON 방어)
     ▼
[API Route]
     ├─ 서버 재정규화: 매체 화이트리스트 + 매체별 필드 격리 + 길이 제한
     ├─ DB insert
     └─ 알림 메일에 동일 정보 포함
```

**클라이언트 캡처 (`useReportRequest.ts`)**

```ts
useEffect(() => {
  try {
    if (window.sessionStorage.getItem(KEY)) return          // 최초 1회만
    const attr = detectAdAttribution(location.search, location.href)
    if (attr.trafficSource !== 'unknown') {                  // unknown은 저장 안 함
      window.sessionStorage.setItem(KEY, JSON.stringify(attr))
    }
  } catch {
    // sessionStorage 차단(시크릿 모드/설정) 시에도 신청 기능은 계속 동작해야 한다
  }
}, [])
```

`try/catch`로 전체를 감싸는 게 중요하다. **부가 기능인 유입 추적이 본 기능인 리드 수집을 막으면 안 된다.**

**서버 재정규화 (`api/report-request/route.ts`)**

```ts
const trafficSource = normalizeTrafficSource(payload.trafficSource)   // 화이트리스트 밖은 unknown

// 매체별 필드 격리 — 구글 유입인데 adKeyword가 왔다면 버린다
const adKeyword     = trafficSource === 'naver'  ? normalize(payload.adKeyword).slice(0, 200)  || null : null
const adCampaignId  = trafficSource === 'google' ? normalize(payload.adCampaignId).slice(0, 100) || null : null
const adCampaignLabel = trafficSource === 'google' ? normalize(payload.adCampaignLabel).slice(0, 100) || null : null
const landingUrl    = trafficSource === 'unknown' ? null : normalize(payload.landingUrl).slice(0, 2000) || null
```

이 삼항 연산자 체인이 **데이터 정합성의 마지막 방어선**이다. 클라이언트가 어떤 조합을 보내든
DB에는 "매체와 모순되지 않는 값"만 들어간다. 길이 제한(200/100/2000)은 클라이언트와 서버 양쪽에 동일하게 적용.

## 5. 이식 체크리스트

새 프로젝트에 적용할 때 순서대로:

- [ ] **마이그레이션 추가** — 위 5개 컬럼 + `traffic_source` CHECK 제약
- [ ] **매체 목록 확정** — 구글/네이버 외에 카카오·메타를 쓰면 판정 파라미터를 추가하고 CHECK 제약도 같이 확장
- [ ] **`detectAdAttribution()` 복사** — 판정 파라미터 배열과 추출 필드만 프로젝트에 맞게 수정
- [ ] **`ATTRIBUTION_STORAGE_KEY` 이름을 프로젝트별로 다르게** — 같은 도메인에 여러 랜딩이 있으면 충돌한다
- [ ] **폼 제출 payload에 5개 필드 첨부**
- [ ] **API에서 서버 재정규화 후 insert** — 매체별 필드 격리 로직을 빠뜨리지 말 것
- [ ] **알림 메일 템플릿에 유입 정보 행 추가** — 영업팀이 DB를 안 봐도 어디서 온 리드인지 알 수 있게
- [ ] **광고 최종 URL에 `c=` 라벨 심기** — 구글 캠페인별로 구분값을 넣어두면 `ad_campaign_label`이 채워진다

**옮길 때 자주 놓치는 것**

1. `unknown`을 sessionStorage에 저장해버리면, 광고 링크로 재진입해도 최초의 `unknown`이 계속 남는다.
2. 서버 재정규화를 생략하면 매체와 무관한 필드가 섞여 들어와 집계 쿼리가 어긋난다.
3. `landing_url` 길이 제한이 없으면 비정상적으로 긴 URL로 insert가 실패할 수 있다.

## 6. 활용 쿼리 예시

```sql
-- 매체별 리드 수
select traffic_source, count(*) from report_request group by 1 order by 2 desc;

-- 네이버 키워드별 리드 (예산 재배분 근거)
select ad_keyword, count(*) from report_request
where traffic_source = 'naver' and ad_keyword is not null
group by 1 order by 2 desc;

-- 구글 캠페인 라벨별 리드
select ad_campaign_label, ad_campaign_id, count(*) from report_request
where traffic_source = 'google'
group by 1, 2 order by 3 desc;
```
